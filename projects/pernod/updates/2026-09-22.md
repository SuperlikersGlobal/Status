# Pernod — actualización 2026-09-22

## Resumen

El 22/09 cerró dos bloques críticos de la V1:

1. freeze local del parser;
2. Submission Ledger validado localmente y contra DynamoDB real.

El camino crítico ahora pasa a **evidencia durable + pipeline retomable**, seguido por elegibilidad, review operacional e integración con Andrés.

## Parser

Se congeló el parser después de implementar soporte seguro para una variante real del Layout 2 donde Textract fusiona contexto, item vendido y cantidad.

Resultado:

- Layout 1 sin regresión;
- Layout 2 original sin regresión;
- variante fusionada reconocida;
- false-credit guards preservados;
- corpus histórico sin cambios inesperados.

El RAW exacto del E2E remoto sigue pendiente antes de un nuevo redeploy.

## E2E / Lambda test

El flujo real de test fue validado:

`WhatsApp → KAPSO → Lambda test → SuperLikers Labs → OCR → parser`

SuperLikers aceptó la evidencia y `distinct_id = email` quedó confirmado.

No hubo deploy de producción.

## Submission Ledger

Se implementó la foundation del ledger con:

- idempotencia;
- claims;
- deduplicación;
- review-first;
- crédito exactly-once;
- reversión append-only;
- kill switch;
- concurrencia segura;
- saldo/eventos reconciliables.

## Multi-beneficiario

Andrés confirmó una regla específica de Pernod:

- un ticket puede generar avance para dos personas;
- ambas reciben el mismo avance;
- sólo una puede redimir/recibir la recompensa.

El modelo fue adaptado para:

`1 documento → 1 autorización → 1–2 ProgressAllocation → 1 reward_owner`

El ticket, OCR, parser y claims no se duplican.

Crédito y reversal de los beneficiarios son atómicos.

## Próximo bloque

**Durable Pipeline**

Objetivo:

```text
submission
→ persist image
→ claim
→ OCR
→ persist RAW OCR
→ fingerprint
→ parser
→ persist parse
→ proposal
→ PENDING_REVIEW
```

El retry debe retomar desde el último estado confirmado y no repetir efectos externos cuando sea evitable.

La evidencia pesada debe almacenarse fuera de DynamoDB, con refs/hashes versionados.
